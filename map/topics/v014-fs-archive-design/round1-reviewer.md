# v0.14 提案评审意见（reviewer round1）

**立场**：补归档标准命令这一小改进无争议、可做；但 **M61 的"INDEX.md 自动维护活文档"设计方向我认为是错的**，且整个提案体量配不上它要解决的低频问题。建议评审通过前把 M60 瘦身、把 M61 从"维护"改造成"生成"。

## 理由 / 风险

1. **M61 是在给 M58 已退役的索引招魂（核心异议）**。M58 删 DB 归档标志位，理由即"位置即状态"——归档 = 移动目录，状态完全由物理位置承载。M61 又以"丢了结构化索引、退化成不透明目录"为由，要做一个"自动维护的活文档"。这等于用文件系统里的第二份数据结构复刻了刚被删掉的索引。
   "位置即状态"的正确推论是：这个索引应是**可派生的投影**——扫描 `map/archive/topics/` 即出表，应当**生成（全量重建）而非维护**。一旦选择"增量 helper + 原子写防并发损坏 + 防 export 双写 + 共用 schema"，就是走进了一条为保持两份状态一致而战斗的路。
   > **红旗判据**：你发现自己要为维护某个索引写并发安全代码的那一刻，就说明这个索引不该被维护，而应改为从源头派生的投影。participant 提出的 INDEX 原子写、host 列出的 R4 双写风险，都是这个错误选择的**症状**，不是需逐一解决的 bug。改成"生成式投影"后，原子写、双写、失时三个问题**自动消失**——它们根本不是真正的问题。

2. **M60 被过度工程化，立项理由是美学而非痛点**。"操作不对称"（F1）不构成 P0 立项依据：`close` 是高频、要鉴权、要 ACK 的命令；归档是低频、纯物理、无副作用的动作（历史共 2 次真实归档）。对称性不是用户价值。真正的"收口"只需 close 成功文案里给 3 行 `git mv` 指引。顺带实锤此点：一条"移动目录"命令要同时伺候 atomic rename、git rename 保真、非 git fallback、防覆盖、`--undo`、索引更新——这些边角正是过度设计的信号。

3. **"零 API 首选"与"无活跃实验关联校验"不可兼得，未闭合**。归档前置校验需补"无活跃实验关联"，而实验关联在 DB；`close` 本就走 API 校验。两者冲突，提案未给出取向：要么接受校验不完整，要么放弃零 API。

## 修订建议（替代方案）

- **M60 瘦身为薄命令**：`map fs archive --topic <slug>` = 解析 slug + 校验「目录存在 & 已 closed & 目标不存在 & 无活跃实验关联（弱校验 + 警告，接受零 API 边界）」+「git 下直接 `git mv`（本身就是原子 rename），非 git fallback `os.rename`」，成功文案输出指引。砍掉独立 `--undo` 的复杂增量逻辑（还原即反向校验 + 移动，一薄层）。
- **M61 改为生成式投影**：提供 `map fs archive-index --rebuild`（或并入 `project export`），扫描 `map/archive/topics/` 全量重建 INDEX.md，不做增量维护、不做并发原子写、不承担"时效责任"——时效由"谁归档谁来扫"保证。schema 与 project export 的 History Export 解耦即可，无需共用 helper 演练双写。
- **验收相应替换**：用"一次 archive → undo 循环后 INDEX 与目录一致（经项目重建验证）"替代"增量更新不破坏表"类逐条验收。

上述第 1 点（M61 方向）与本条第 2、3 点建议作为评审通过的前置判断依据；M60 薄命令本身可独立先落。
