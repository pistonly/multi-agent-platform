## 变更摘要

| 领域 | 现状 | v0.14 目标 |
|------|------|-----------|
| 话题归档操作 | 无标准入口：CLI 只在引导文案提示手动 `mv`（`cli/commands/topic.py` archive 分支）；`close` 有 `map fs close` 封装而 `archive` 没有，**操作不对称** | 新增 `map fs archive --topic <slug>`（及 `--undo`），复用现有 `map fs` 命令族模式；FS 话题归档 = 受校验的文件移动 |
| 归档索引 | `map/archive/INDEX.md` 是 `map project export` 生成的只读快照，不随归档动作更新 | 归档/还原时**自动维护** `map/archive/INDEX.md`（追加/移除条目），保持可查询 |

## 背景与动机

v0.13 M58 移除 DB archive 标志位，归档收敛为「移动 `map/topics/<slug>/` → `map/archive/topics/`」。但这条收敛**只做了一半**：命令族语义不对称，且归档索引缺失。

- **操作不对称（核心痛点）**：`map fs` 已有 `close` / `comment` / `advance-round` / `topic create` 等命令（见 `cli/commands/fs.py` 文件头注释分类），但 **archive 没有 `fs archive` 对应物**——仅在 `topic.py` 的 `_DB_WRITE_RETIRED` 引导文案里写死 `mv map/topics/<slug>/ map/archive/topics/` 提示（v0.13 L410–418）。多 Agent 协作中，「关话题有标准命令、归档要手敲 `git mv`」这种不对称极易导致归档动作被遗漏或误操作（忘记先 close、移动后更新索引、用 `cp` 而非 `mv` 留下 ghost 目录）。
- **索引缺失（可查询性退化）**：`map/archive/INDEX.md` 由 `map project export` 在 2026-08-14 生成后未再更新（其中 2 个归档话题的 Status 仍为 open，与实际不符）。DB 版 archive 是记录级可查询标志；FS 化后丢失了结构化索引，退化成一个不透明的目录。
- **`map work` 扫描语义隐式依赖路径**：exp 与 topic 待办扫描 `map/topics/`，归档后自动退出扫描面是**良性副作用**，但目前依赖「物理路径改变」这一隐式约定，无命令做校验，易出现 ghost topic。

> 定位：本提案是**工程卫生清偿版**，不新增领域能力，补齐 M58 遗留的操作对称性与索引缺口。与 v0.13「清偿版」定位一致。

### 证据清单

| # | 来源 | 事项 | 现状验证（2026-08-22） |
|---|------|------|----------|

| F2 | `map/archive/INDEX.md` | 归档索引是 `project export` 只读快照，未随归档更新 | 文件头 `Generated by map project export`（2026-08-14）；其中 2 个归档话题 `Status: open`，与实际状态不符 |

## 设计原则

1. **与 M58 收敛方向自洽**：归档仍是「位置即状态」的文件移动，不复辟 DB 标志位；`fs archive` 只是给这个移动加**标准入口 + 前置校验 + 索引维护**，内部仍走 `git mv` 级原子移动。
2. **操作对称**：`close` 有标准命令，`archive` 必须有对应标准命令；二者都进 `map fs` 命令族，帮助文案由「手敲 `mv`」升级为「调 `map fs archive`」。
3. **索引自动维护**：归档/还原时增量更新 `map/archive/INDEX.md`，不靠人工编辑，不依赖 `project export` 只读快照。
4. **零 API 首选**：归档是纯文件操作（参考 fs.py 第一类命令），默认零网络；`close` 校验走 API（第二类）——归档只需校验「已 closed + 目录存在」，可纯本地完成。

## M60 `map fs archive` 命令（P0）

> **目标**：补齐 F1，为 FS 话题归档提供标准入口，消除与 `close` 的操作不对称。

**CLI 接口**（加入 `cli/commands/fs.py` 的 `fs_app`）：

```
map fs archive --topic <slug> [--undo] [--persona <name>]
```

**行为**（`archive` 方向）：

1. **解析目标**：`<slug>` → 检查 `map/topics/<slug>/index.md` 存在（`_fs_slug_by_uuid` + 目录存在性，可复用 `topic.py` 的 `_resolve_topic_ref` 或 fs.py 本地解析）。
2. **前置校验**（任一不满足则 `exit 2` 并给引导信息，不静默成功）：
   - 目录存在且含 `index.md`；
   - `index.md` frontmatter `status: closed`（**归档必须是收口后动作**；未 closed 的提示先 `map fs close`）；
   - 目标 `map/archive/topics/<slug>/` 不存在（避免覆盖）。
3. **校验通过**：把 `map/topics/<slug>/` **整体移动**到 `map/archive/topics/<slug>/`。移动采用 `shutil.move`（目录级原子性），并在成功后尝试调用 `git mv` 语义——若 workspace 是 git 仓库则用 `git mv` 保留 rename 历史（尽力而为，非 git 环境 fallback 到 `os.rename`）。
4. **索引维护**：调用共享的索引更新 helper，向 `map/archive/INDEX.md` 的 Topics 表**追加该话题条目** 或刷新已有条目（标题、closed、decision 取自 close note、`File` 相对路径）。

**`--undo`（还原）方向**：做反操作——

1. 校验 `map/archive/topics/<slug>/index.md` 存在；
2. 移动回 `map/topics/<slug>/`；
3. 从 `map/archive/INDEX.md` **移除**对应行（保留 Topics 表结构与表头）。

**输出**：默认人类可读摘要（`archived <slug> → map/archive/topics/`），支持 `--format json/yaml`（对齐 M54A 机器可读约定）。

**与现有模式的关系**：
- 复用 `cli/commands/fs.py` 的 `_workspace()` / `_content_root_name()` / persona 解析；
- 帮助文案：`map fs archive --help` 补充归档语义说明；
- `topic.py` `_DB_WRITE_RETIRED["archive"]` 引导文案更新为「FS 话题用 `map fs archive --topic <slug>`」（仅 DB 遗留 topic 提示走旧说明）。

**验收**：
1. host persona 对已 closed 的 FS 话题 `map fs archive --topic v012-ergonomics-review` 成功，`map/archive/topics/v012-ergonomics-review/` 出现、`map/topics/` 消失；
2. 未 closed 话题归档被拦截并提示先 close（exit 2）；
3. 归档后 `map/archive/INDEX.md` 自动出现该话题条目且表结构完好；
4. `--undo` 成功还原并移除索引条目；
5. git 仓库下操作为 rename（`git status` 显示 `renamed:` 而非 `deleted:+untracked`）；
6. fast-gate 无回归。

## M61 归档索引统一模型（P1）

> **目标**：补齐 F2，把「归档索引」从 `project export` 只读快照升级为**自动维护的活文档**。

**设计**：提炼共享 helper（如 `cli/fs_archive.py` 的 `update_archive_index(archive_root, slug, meta, remove=False)`），M60 归档/还原命令与 `project export` 共用同一 schema，避免两套 INDEX 格式漂移。

**`map/archive/INDEX.md` Schema（Topics 表收敛为）**：

```
| Title | Status | Decision | Notes | File |
|-------|--------|----------|-------|------|
| MAP 平台瘦身：本地 MD 文档为主，平台作为交互索引 | closed | no | 2026-08-14 归档 | [topics/<slug>.md](topics/<slug>.md) |
```

- `Status`：归档条目统一记 `closed`（若还原则移除）；
- `Decision`：取自 index.md close note 的 `decision` 字段（缺失则 `no`）；
- `Notes`：归档时间戳 + 可选原因；
- `File`：相对路径（目录形态 `<slug>/` 或文件形态 `<slug>.md` 依实际落位）。

**边界**：
- `project export` 的 History Export 仍可保留（全量快照语义），但**归档专用 INDEX 由 helper 维护**，不再依赖它保证时效；
- 归档话题目录内部结构、相对引用在移动前做一次**链接健壮性检查**（grep 话题目录内是否有对 `..` 或 `map/topics/` 的引用，有则警告提示，不阻断——与「位置即状态」妥协，见设计原则 1）。

**验收**：
1. 一次 archive → undo 循环后，`map/archive/INDEX.md` Topics 表与目录状态一致；
2. 多次归档累积不产生重复行、不破坏表头；
3. `project export` 与 `map fs archive` 两种写入不互相覆盖产生格式错误。

## 非目标

- **不复辟 DB archive 标志位**：DB 记录仍按 M58 保持只读。
- **不做多话题批量归档 UI/命令**：一次一个 `--topic`，批量演进后续再说（YAGNI）。
- **不引入新的待办状态**：归档目录不产生 waker 待办，退出扫描面即最终态。

## 风险与决策

| # | 风险 / 悬置 | 判定 | 依据 |
|---|-------------|------|------|
| R1 | 归档后的 topic 如何再「重新激活」讨论 | `--undo` 还原回 `map/topics/` 即重新进入扫描面；无需新状态 | 位置即状态，M58 既定语义 |
| R2 | 相对链接在移动后失效 | 归档前做链接健壮性检查并**警告**（不阻断）；纯 Markdown 话题多为单文件，风险低 | F3：当前话题均为单 index.md 形态 |
| R3 | 非 git workspace 场景的 rename 保真 | `git mv` 为尽力而为；失败 fallback `os.rename`，功能不阻断 | M60 第 3 步 |
| R4 | INDEX.md 与 `project export` 双写冲突 | 共用同一 schema + 同一 helper；export 不再承担归档索引的时效责任 | M61 |

## 里程碑依赖

- M60 独立可交付（P0，先做）；
- M61 依赖 M60 的 helper 抽取（P1，紧接）。

## 验收总览（最终用户视角）

- 话题收口链条现在**三态都有标准命令**：`fs close` → `fs archive`（+`--undo`），不再需要手敲 `git mv`；
- 归档后 `map fs list` / `map work` 自动忽略已归档话题，`map/archive/INDEX.md` 保持当前可查询；
- git 历史完整保留 rename，审计无断层。
