## 定稿依据（争议闭合记录）

### 争议 1：废弃 vs 修复 → 废弃定案

reviewer 四条独立证据（round2-reviewer.md）：

1. **修复面远大于「加个 webhook」**：`platform_feedback_service` 全文零 notification 调用，提交后无任何收件人提醒机制；真修需补 webhook 集成 + 凭据管理 + 重试队列 + triage 闭环 = 在 MAP 核心重建简化版 issue tracker，违反薄核心定位
2. **triage 可见性实测为零**：`feedback list/get/update` 为 admin-token-only，三个协作 persona 全部无读权限——「读者」在角色模型之外
3. **结构性劣势不可修**：单向消息 vs GitHub issue 的评论线程 / MAP 话题的轮次分诊——单向收件箱是两条既有通道的下位替代
4. **自托管经济学**：webhook 转发要求部署者配置上游凭据，开源自托管回传配置率趋零

participant 补强（清账过程新证据）：**10/10 已修却 0/10 被标 resolved**——修复者从不回 feedback 通道关单，死信箱连「闭环记账」最低功能都从未发生；修复全走「直接指挥 → commit → 测试锁定」旁路。

### 争议 2-4 定稿要点

- **清账口径**：participant 核证 10/10 已修或已随 M58 退役消亡，**转 GitHub issue 分支为空集**；host 持 admin token CLI 逐条 `update --status resolved`；处置表为 DB 只读化后唯一人类友好索引
- **stub 边界**：admin triage 入口同拆（`update` 与只读承诺直接矛盾）；四命令统一 exit 2，文案两行分流 + 「历史数据只读保留」提示
- **SDK**：5 方法（`submit_feedback` / `list_feedback` / `list_feedback_page` / `get_feedback` / `update_feedback`）全删无方法级 stub——**breaking change**（本条即 reviewer 所要求的 breaking 记录；仓库无 CHANGELOG 惯例，以本 PRD 为载体）。理由：0.x minor 允许 breaking；端点拆除后方法必撞 404，留着是坏接口；SDK 调用方是代码，AttributeError 即标准 breaking signal
