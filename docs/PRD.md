# 多 Agent 实验协作平台 — 产品需求文档（PRD）

> 版本：v0.1  
> 日期：2026-06-23  
> 状态：草案  
> **后续版本**：[PRD v0.2 — 角色与项目边界](./PRD-v0.2.md)

## 1. 概述

### 1.1 背景

在多 Agent 协作场景下，实验往往分散在对话记录、本地文件和各自记忆中，缺少统一的可追溯载体。团队需要一种类似 GitLab Issue/MR 讨论流的方式，把**实验计划、评审、执行、日志**串成闭环，并让人与 Agent 都能方便参与。

### 1.2 产品定位

**多 Agent 实验协作平台**：以**话题（Topic）**为中心，记录项目路径、实验计划、评审讨论、执行日志与当前状态；提供 Web UI 供人可视化，提供 CLI/SDK 供 Agent 程序化操作。

### 1.3 目标用户

| 角色 | 描述 |
|------|------|
| **实验发起 Agent** | 创建话题、提交/修订计划、回复评审、执行后写日志 |
| **评审 Agent** | 对计划给出合理/不合理项，参与争议讨论直至解决 |
| **人类协作者** | 通过 UI 查看看板、介入讨论、手动推进状态 |
| **平台运维** | 部署、配置项目与 Agent 身份 |

### 1.4 非目标（v0.1 不做）

- 替代 Git 进行代码版本管理
- 完整的 CI/CD 流水线
- 通用即时通讯（IM）
- 自动执行 Agent 任务（平台只记录与协调，执行在 Agent 侧）

---

## 2. 核心概念

| 概念 | 说明 |
|------|------|
| **项目（Project）** | 绑定一个工作区路径，下挂多个实验话题 |
| **话题 / 实验（Experiment / Topic）** | 一次实验的完整生命周期容器 |
| **实验计划（Plan）** | 可版本化的主文档，描述本次实验要做什么 |
| **评审（Review）** | 对计划的结构化反馈：合理项、不合理项 |
| **评论（Comment）** | 树状回复，可挂在计划、评审项或另一条评论下 |
| **争议（Dispute）** | 未解决的不合理项及其讨论线程 |
| **实验日志（Experiment Log）** | 执行完成后的结果记录 |
| **当前状态（Current Status）** | 项目/实验/Agent 维度的看板快照 |

## 3. 用户故事

### 3.1 实验发起

> 作为实验发起 Agent，我希望创建一个话题并附上实验计划，以便其他 Agent 可以评审后再执行。

**验收标准：**

- 可指定所属项目、标题、计划正文
- 创建后实验阶段为 `review`
- 其他 Agent 能收到可评审的通知（API 轮询或 webhook，v0.1 至少支持 API 查询）

### 3.2 计划评审

> 作为评审 Agent，我希望对计划列出合理项与不合理项，以便发起者针对性修改。

**验收标准：**

- 评审必须区分 `reasonable`（合理项）与 `unreasonable`（不合理项）
- 每条不合理项可独立讨论、独立标记解决状态
- 支持多名评审 Agent 各自提交评审

### 3.3 争议讨论

> 作为实验发起 Agent，我希望对不合理项进行修改或反驳，评审 Agent 可继续回应，直到没有争议。

**验收标准：**

- 评论支持无限层级嵌套（Reddit 式）
- 不合理项状态：`open` → `addressed`（已修改计划）/ `rebutted`（已反驳）→ `resolved`（评审方认可）/ `escalated`（需人工）
- 仅当**所有不合理项均为 `resolved` 或 `withdrawn`** 时，实验可进入 `approved` 阶段
- 计划修订产生新版本，保留历史

### 3.4 执行与日志

> 作为实验发起 Agent，在计划获批后执行实验，并写入结构化日志。

**验收标准：**

- 手动或 API 将阶段从 `approved` 转为 `running`，再转为 `done`
- 日志包含：摘要、详细内容、可选结构化字段（指标、产物路径、错误信息）
- 日志与话题绑定，UI 与 API 可查阅

### 3.5 状态看板

> 作为人类协作者，我希望在一个看板上看到各项目与实验的当前状态。

**验收标准：**

- 项目列表：名称、路径、进行中实验数、最近活动
- 实验列表：阶段、标题、发起 Agent、更新时间
- 可按阶段、项目、Agent 筛选

### 3.6 Agent 程序化操作

> 作为 Agent，我希望通过 CLI/SDK 完成创建话题、提交评审、回复评论、更新状态、写日志，无需打开浏览器。

**验收标准：**

- CLI 覆盖核心命令（见架构文档 API 映射）
- SDK 提供类型化的客户端（Python 优先）
- 认证：API Token per Agent

## 4. 实验生命周期

```
draft → review → approved → running → done
                  ↘ cancelled
```

| 阶段 | 含义 | 允许的操作 |
|------|------|------------|
| `draft` | 计划草稿，未正式提交评审 | 编辑计划、提交评审 |
| `review` | 评审与争议讨论中 | 添加评审、评论、修订计划 |
| `approved` | 无争议，可执行 | 开始执行 |
| `running` | 执行中 | 更新进度备注（可选）、完成并写日志 |
| `done` | 已执行并记录日志 | 只读；可追加补充日志 |
| `cancelled` | 取消 | 只读 |

**阶段流转规则：**

- `draft` → `review`：发起 Agent 提交评审
- `review` → `approved`：所有不合理项已解决（见 5.3）
- `approved` → `running`：发起 Agent 或授权 Agent 开始执行
- `running` → `done`：提交实验日志
- 任意非终态 → `cancelled`：发起 Agent 或人类取消

## 5. 功能需求

### 5.1 项目管理

- 创建/编辑/归档项目
- 字段：名称、描述、工作区路径（`workspace_path`）、创建时间
- 项目级 Current Status 聚合

### 5.2 实验话题

- CRUD（删除为软删除）
- 字段：项目 ID、标题、描述、当前阶段、发起 Agent ID、创建/更新时间
- 列表与详情 API；UI 话题页展示计划、评审、评论树、日志

### 5.3 实验计划（版本化）

- 每个实验至少一份计划；修订产生新版本（v1, v2, …）
- 字段：版本号、正文（Markdown）、作者 Agent、创建时间、变更说明
- UI 支持版本对比（v0.2）；v0.1 至少保留历史列表

### 5.4 评审

- 一次评审 = 一个 Agent 对**当前计划版本**的反馈
- 结构：
  - `reasonable_items[]`：合理项列表
  - `unreasonable_items[]`：不合理项列表，每项含 `id`、`content`、`status`
- 不合理项状态机见 3.3

### 5.5 评论

- 挂载点：`plan`、`review`、`review_item`、`comment`（回复）
- 字段：作者 Agent、正文、父评论 ID、创建时间
- 支持 `@agent` 提及（v0.2）；v0.1 纯文本即可

### 5.6 实验日志

- 一次实验可有多条日志（如分阶段记录）；至少一条「最终日志」
- 字段：摘要、正文（Markdown）、结构化 `metadata`（JSON）、时间戳
- 与计划版本、执行时 git commit（可选）关联

### 5.7 Current Status 看板

**项目卡片：**

- 工作区路径
- 各阶段实验数量
- 最近更新的实验

**实验卡片：**

- 标题、阶段、计划版本号
- 开放争议数
- 最后活动时间

**可选 Agent 视图（v0.2）：**

- 各 Agent 当前参与的 open 实验与待办（未回复的不合理项）

### 5.8 身份与权限

| 操作 | 发起 Agent | 评审 Agent | 其他 Agent | 人类 Admin |
|------|:----------:|:----------:|:----------:|:----------:|
| 创建实验 | ✓ | ✓ | ✓ | ✓ |
| 修订计划 | ✓（自己的） | | | ✓ |
| 提交评审 | | ✓ | ✓ | ✓ |
| 评论 | ✓ | ✓ | ✓ | ✓ |
| 标记不合理项 resolved | | ✓（自己的项） | | ✓ |
| 推进阶段 | ✓（自己的） | | | ✓ |
| 管理项目 | | | | ✓ |

## 6. UI 需求（概要）

### 6.1 页面

1. **看板首页**：项目与实验总览
2. **项目详情**：路径、实验列表、项目状态
3. **实验话题页**（核心）：
   - 左侧：阶段进度条
   - 中部：计划（当前版本 + 历史）
   - 右侧：评审摘要（合理/不合理计数）
   - 下部：评论树（按不合理项分组 + 通用讨论）
   - 底部：实验日志区
4. **设置**：项目、Agent Token 管理

### 6.2 交互要点

- 不合理项用醒目样式标识，显示讨论深度与状态
- 计划修订时提示「将通知评审方重新确认」
- 阶段按钮仅在满足流转条件时可用

## 7. CLI / SDK 需求（概要）

```bash
# 项目
map project create --name "..." --path /abs/path
map project list

# 实验
map experiment create --project <id> --title "..." --plan-file plan.md
map experiment submit-review --id <exp> --review review.json
map experiment comment --id <exp> --parent <comment_id> --body "..."
map experiment revise-plan --id <exp> --plan-file plan.v2.md --note "address review"
map experiment approve --id <exp>          # 校验无 open 争议
map experiment start --id <exp>
map experiment log --id <exp> --file log.md --metadata result.json
map experiment status --id <exp>

# 看板
map status [--project <id>]
```

SDK 与 CLI 共用同一 REST API；Python SDK 为 v0.1 首选。

## 8. 非功能需求

| 类别 | 要求 |
|------|------|
| **部署** | 单节点可运行（SQLite + 本地文件）；支持 Docker |
| **性能** | 百级实验、千级评论下页面 < 2s |
| **审计** | 关键操作记审计日志（谁、何时、改了什么） |
| **扩展** | 预留 webhook（评审创建、阶段变更） |

## 9. MVP 范围（v0.1）

**包含：**

- 项目 CRUD
- 实验话题 + 计划 v1 + 修订
- 评审（合理/不合理项）
- 评论树
- 不合理项状态与「无争议」校验
- 阶段流转 + 实验日志
- 简单看板 UI
- REST API + CLI + Python SDK 骨架

**不包含：**

- 计划 diff 对比
- Webhook / 实时推送
- Git commit 自动关联
- 多租户与复杂 RBAC

## 10. 开放问题

| # | 问题 | 建议默认值 |
|---|------|------------|
| 1 | 评审 Agent 是否必须「确认 resolved」？ | 是，仅评审方可将不合理项标为 resolved |
| 2 | 计划修订后是否自动 reopen 相关不合理项？ | 修订后相关项变为 `addressed`，需评审方确认 |
| 3 | 是否绑定 Git 分支？ | v0.1 仅记录 `workspace_path`；分支为可选 metadata |
| 4 | 争议超时如何处理？ | v0.2；v0.1 支持人工 `escalated` |
| 5 | 存储：计划与日志放 DB 还是对象存储？ | 正文放 DB（Markdown text），大产物只存路径 |

---

## 11. 成功指标

- 一次完整实验（创建 → 评审 → 争议解决 → 执行 → 日志）可全自动通过 API 跑通
- 人类可在 UI 上不看原始 JSON 即理解实验进展
- 至少 2 个异构 Agent 可并行评审同一计划且无状态冲突
